# 业务蓝图格式标准

> 文件定位：本文件规定《业务蓝图说明书》（业务需求说明书）的**文档格式、章节框架、编号规则、枚举值、图示与用词口径**。编写流程与确认机制见《业务蓝图编写规范.MD》，两文件冲突时以本文件为准。
>
> 版本说明：V1.1（2026-11-24 重建）。原 V1.0 文件在库中缺失，本版依据 `00.参考规范/【LWMS】…物流拉动仓储业务蓝图说明书.docx` 的格式骨架、以及本仓库已产出的 V0.2 骨架与 14 张场景卡反推重建；**只保留格式与占位符，不包含 LWMS 业务内容**。重建版须经用户确认后方可作为编写依据。

---

## 一、适用范围

适用于 OMS / TMS / BMS 各业务域的《业务蓝图说明书》。本文件只管"长什么样"，不管"写什么业务内容"。

---

## 二、文档章节框架

### 2.1 整体框架

| 层级 | 标题 | 必备内容 |
|---|---|---|
| 封面 | — | 项目名称、文档名称（业务蓝图说明书·业务范围）、公司、产品线、文档类型、工作产品名称 |
| 文档信息 | 文档信息表 | 当前版本号、文档负责人、创建日期、最近更新日期、最近更新人、作者、对应里程碑、上游输入、文档约定 |
| 文档审批 | 审批表 | 部门、审批人角色、审批人姓名、签字、日期（空行待签） |
| 第 1 章 | 概述 | 见 2.2 |
| 第 2 章 | 业务流程和业务场景 | 见 2.3 |
| 第 3 章 | 业务需求 | 场景卡，见第四节 |
| 附录 | 附录 A、B、C… | 可选。承接蓝图中的架构、集成、规则库、开放项等非场景内容；每篇附录首行注明"承接自《…》第 N 章，内容未改写" |

### 2.2 第 1 章 概述

| 小节 | 标题 | 必备内容 |
|---|---|---|
| 1.1 | 目的（项目背景） | 文档用途的固定表述 + 本项目承担的具体任务（编号列表） |
| 1.2 | 需求范围 | 系统覆盖范围、本期范围外/后置项、**业务部门及范围表**（部门｜业务范围）、预期读者 |
| 1.3 | 引用/参考 | 表：文件｜说明，逐条列出上游输入材料 |
| 1.4 | 系统的业务用户 | 每个用户类别一张表，字段见 2.2.1 |
| 1.5 | 业务词汇表 | 表：业务名词/术语｜描述，覆盖全文出现的缩写与专有名词 |

#### 2.2.1 业务用户表字段

| 字段 | 取值/要求 |
|---|---|
| 名称 | 用户群名称 |
| 类别 | 枚举：决策人 / 管理者 / 使用人 |
| 相关度 | 枚举：高 / 中 / 低 |
| 影响度 | 枚举：高 / 中 / 低 |
| 代表 | 具体岗位或人员（未知写"待补充"） |
| 联系方式 | 未知写"待补充" |
| 职责 | 一句话职责 |
| 核心关注点 | 子表：编号｜内容｜重要度（枚举：高 / 中 / 低） |
| 备注 | 可空 |

### 2.3 第 2 章 业务流程和业务场景

| 小节 | 标题 | 必备内容 |
|---|---|---|
| 2.1 | 整体业务流程 | 一张全景 mermaid 流程图 + 图例；场景框内标注场景编号，与 2.2、2.3 清单对应 |
| 2.2 | 业务流程说明 | 表：场景编号｜类型｜流程名称｜简要说明｜优先级（列顺序固定）；只放端到端核心业务流程 |
| 2.3 | 业务场景说明 | 表：场景编号｜类型｜流程名称｜简要说明｜优先级；只放由核心流程派生的模式化场景 |

流程与场景必须分列两节，不得合并为一张大清单；两节合计即为第 3 章场景卡全集。

## 三、编号、命名与枚举

### 3.1 场景编号

格式：`<域代码>.<二级域>.<系统代码>.<三位流水号>`，示例 `TP.01.TMS.001`。

| 段 | 取值 | 说明 |
|---|---|---|
| 域代码 | TP（运输）/ OP（订单）/ BP（结算）等 | 与项目蓝图编号体系一致 |
| 二级域 | 01 入厂物流、02 整车物流、03 售后备件… | 由项目定义并登记 |
| 系统代码 | TMS / OMS / BMS | 大写 |
| 流水号 | 001 起三位 | 连续、不跳号、不复用；删除场景保留空号并在 2.2 清单注明，不重排后续编号 |

### 3.2 子流程编号

同一场景内存在并列分支流程时，用 `-n` 后缀：`TP.01.TMS.001-1`、`TP.01.TMS.001-2`。最多两级；子流程必须在场景卡标题下单独成节，不得只在正文提及。

### 3.3 活动步骤编号

| 规则 | 说明 |
|---|---|
| 位数 | 固定三位数字，与"流程步骤"分列 |
| 起始与步长 | 010 起，常规步骤每次 +10（010、020、030…） |
| 分支/判断 | 以父步骤号 + 尾数表示（如 030 下的两个分支为 031、032） |
| 插入 | 插入步骤占用中间号（015、025），**不重排已有编号** |
| 唯一性 | 同一张场景卡内唯一且单调递增 |
| 对应关系 | 业务流程图中的判断节点必须能在活动步骤表中找到对应编号 |

### 3.4 枚举值（全文只允许使用下表取值）

> 枚举列在信息未闭环时允许填"待补充"（不得臆造取值），但须同步列入附录开放项或批次末"待补充"清单，定稿前清零。

| 枚举类别 | 允许值 | 使用位置 |
|---|---|---|
| 流程类型 | 计划 / 执行 / 监控 | 2.2、2.3 清单"类型"列 |
| 优先级 | 关键 / 重要 / 一般 | 2.2 清单、用例简述表 |
| 用例类型 | 新增 / 修改 / 无变化 | 场景卡第（8）部分 |
| 用户类别 | 决策人 / 管理者 / 使用人 | 1.4 业务用户表"类别" |
| 相关度、影响度、重要度 | 高 / 中 / 低 | 1.4 业务用户表 |
| 终端 | PC / 移动端 / PDA / 大屏 / 其他 | 需区分终端时（角色映射、用例简述备注） |
| 状态标注 | 【已确认】/【设计建议】/【待确认】/【待补充】 | 全文，口径见第六节 |

### 3.5 文件命名

格式：`<系统>业务蓝图方案_<业务范围>_V<主版本>.<次版本>_<YYYYMMDD>.md`（Word 同主名 `.docx`）。

- 示例：`TMS业务蓝图方案_零部件入厂物流_V0.2_20261124.md`
- 存放目录：`01.需求管理`
- 版本：V0.x 草案（未评审）；V1.0 评审通过；修订以 `Rev.n` 标注在文档信息"版本修订"行
- 同一主版本只保留一份当前文件，历史版本不并存于 `01.需求管理`

### 3.6 标题与表头口径

- 章节标题一律带编号：`# 1 概述`、`## 1.1 目的（项目背景）`、`## 3.1 TP.01.TMS.001-计划接收业务场景`
- 表头列名固定，不得增删改列（各表列定义见第四节）
- 表格内不写合并单元格的多层表头；需要分组时拆表

## 四、场景卡结构

### 4.1 场景卡标题

`## 3.<n> <场景编号>-<流程名称>业务场景`

- `<n>` 与 2.2 清单顺序一致，从 3.1 连续编号
- 场景编号与清单完全一致，不得出现清单有卡无、卡有清单无

### 4.2 与 2.2 清单的一致性

- 每张卡对应清单一行；卡的"流程名称"与清单"流程名称"逐字一致
- 新增/删除/改名场景：先改 2.2 清单并重新确认，再改卡
- 清单"类型""优先级"变更同步到卡内相关内容

### 4.3 场景卡八部分

每张卡严格按下列顺序输出，标题使用加粗序号（`**（1）基本信息**`）：

| 序号 | 部分 | 形式 | 必备字段 |
|---|---|---|---|
| （1） | 基本信息 | 表：项目｜内容，固定 4 行 | 业务流程编号、业务流程名称、流程简要说明、业务流程描述（通常填"见下图"） |
| （2） | 业务流程图 | mermaid 流程图 + 图例 | 覆盖（4）中全部活动步骤与判断分支 |
| （3） | 流程相关文档/表单 | 表：文档/表单名称｜流程环节｜说明（包括获得方式） | 每份单据注明来源系统或产生方式 |
| （4） | 流程相关规则（活动步骤表） | 表：流程编号｜流程步骤｜输入｜活动描述｜输出｜责任部门｜备注 | **场景卡核心，不得以文字段落替代** |
| （5） | 变化可能/关键例外 | 列表 | 逐条列出参数未定、口径不一、接口/审批异常等 |
| （6） | 用例图 | mermaid 用例图 + 图例 | 角色与用例的关联；可整体裁剪，见 4.4 |
| （7） | 角色—最终用户映射表 | 表：角色｜最终用户 | 角色须为（6）中出现的角色；可整体裁剪，见 4.4 |
| （8） | 用例（业务功能）简述 | 表：类型｜用例名称｜用例简述｜优先级 | 类型取"新增/修改/无变化"，与（5）呼应；可整体裁剪，见 4.4 |

#### 4.3.1 活动步骤表填写规则

- "输入""输出"必须是**名词**（单据、数据、状态），不得写动作
- "活动描述"写"谁在什么条件下做什么、系统做什么"，一句话说清
- "责任部门"必须出现在 1.2 业务部门及范围表中；系统动作写系统名（如 TMS）
- 判断步骤的输出写明各分支去向（如"通过 → 040；不通过 → 031"）
- 规则未闭环的内容写进"备注"并标注【待确认】，不得写进正文冒充结论

### 4.4 裁剪规则

| 部分 | 可否裁剪 | 条件与写法 |
|---|---|---|
| （1）（2）（4）（5） | 不可裁剪 | — |
| （3）流程相关文档/表单 | 可裁剪 | 全流程确无单据时，保留标题并写"本场景无流程单据" |
| （6）（7）（8） | 可整体裁剪 | 业务蓝图只承担流程与需求、功能设计交由 PRD 承接时，三部分整块裁剪；须在文档信息或 1.1 中说明，裁剪后卡片保留（1）–（5），三部分不逐个保留标题 |
| （7）角色—最终用户映射表 | 可单独裁剪 | 保留（6）（8）而本场景无人工角色时，写"本场景无人工角色，裁剪" |

裁剪必须写明原因；除（6）（7）（8）整块裁剪外，不得直接删除标题。

> 执行说明：TMS《零部件入厂物流》V0.2 起按"整块裁剪"处理，（6）（7）（8）由后续 PRD 承接。

## 五、图示规范

### 5.1 业务流程图（第（2）部分与 2.1）

- 使用 mermaid `flowchart`（LR 或 TB），不得使用 mermaid 不支持的 UML 语法
- 矩形 = 活动；菱形 = 判断；虚线 = 兜底/异常路径；子图 = 系统边界或阶段
- 节点文字与活动步骤表的"流程步骤"一致；判断节点带分支标签
- 涉及 3 个及以上部门的卡，建议用泳道（`subgraph` 按部门分组）
- 图下必须有 `图例：` 一行，说明线型、形状、颜色含义

### 5.2 用例图（第（6）部分）

- 使用 mermaid `flowchart` 近似表达：角色 `A(["角色"])`，用例 `UC1(用例名)`，`subgraph` 表示场景边界
- 角色须来自 1.4 业务用户或 1.2 部门清单；用例须与第（8）部分逐条对应
- 图下必须有 `图例：` 一行

### 5.3 可渲染性

- 节点文本含括号、斜杠、冒号等特殊字符时用双引号包裹
- 换行统一用 `<br>`
- 输出前必须实际渲染验证，不得提交无法渲染的语法

### 5.4 Word 输出

- mermaid 图在 Word 中必须**渲染为图片插入**（保留图注），不得只留代码块
- 图片清晰度不低于 150 dpi，宽度适配 A4 正文区
- 图注格式：`图 3-1 <图名>`

## 六、用词与内容口径

### 6.1 状态标注

| 标注 | 含义 | 使用要求 |
|---|---|---|
| 【已确认】 | 调研/评审已明确的业务事实 | 可直接作为需求输入 |
| 【设计建议】 | 编写方提出、待评审确认 | 须在第（5）部分或开放项中列明 |
| 【待确认】 | 调研未闭环，需业务/IT 书面答复 | 不得作为开发输入 |
| 【待补充】 | 材料缺失的字段/信息 | 批次末汇总列出 |

### 6.2 名词口径

- 系统名统一用代码：TMS / OMS / BMS / WMS / SRM / SAP / APS / OA
- 同一概念全文只用一种叫法，首次出现处进 1.5 词汇表
- 部门名必须与 1.2 表一致，不得简称与全称混用
- 单据名带"单/表/证/清单"等名词后缀

### 6.3 禁止事项

- 禁止臆造业务规则、单据、部门、数量、比例等任何事实性内容
- 禁止以文字段落替代表格（活动步骤表、用例简述表）
- 禁止空章节写"略"或留空无说明；缺失信息写"待补充"并进汇总清单
- 禁止在场景卡中引入清单外的场景或拆分出未登记的编号
