## 1. 目的与适用范围

本规范约束 OTWB 项目全部产品需求文档的目录结构、编号规则、模板结构、写作格式与版本管理，保证：

1. 文档体系一致、可索引、可追溯；
2. 任何新成员能按统一模板快速读懂和续写文档；
3. 需求、PRD、原型三者编号可互相关联。

本规范对全部撰写、修订 PRD 的人员生效；与《PRD-OTWB-000-顶层设计》冲突时，以顶层设计为准并回改本规范。

## 2. 目录结构规范

```
03.PRD管理\
├── PRD-OTWB-000-顶层设计.md         顶层文件（唯一，放根目录）
├── 00-总体规范\                      横切规范文档（PRD规范/术语表/状态机规范/接口规范…）
├── 01-基础资料MDM\                   PRD-MD-xxx
├── 02-订单管理OMS\                   PRD-OM-xxx
├── 03-运输管理TMS\                   PRD-TM-xxx
└── 04-结算管理BMS\                   PRD-BM-xxx
```

规则：

1. 服务文件夹按顶层设计 2.2 节服务总览划分，不得自行新增服务文件夹；新增需先修订顶层设计；
2. 每个文件夹内文档数量较多时，可按模块增设二级子目录（如 `03-运输管理TMS\配载\`），二级目录命名使用模块中文名；
3. 文档只存放于归属服务的文件夹；跨服务功能以属主服务为准编写，其他服务文档仅引用编号，不重复定义。

## 3. 文档编号规范

### 3.1 编号格式

```
PRD-<域码>-<三位流水号>-<文档名称>.md
```

| 域码 | 含义 | 示例 |
| --- | --- | --- |
| OTWB | 顶层 | PRD-OTWB-000-顶层设计.md |
| SPEC | 横切规范（00-总体规范内） | PRD-SPEC-001-PRD总体规范.md、PRD-SPEC-002-统一术语表.md |
| MD | 基础资料 MDM | PRD-MD-001-客户主数据.md |
| OM | 订单管理 OMS | PRD-OM-001-销售订单.md |
| TM | 运输管理 TMS | PRD-TM-001-发货订单.md |
| BM | 结算管理 BMS | PRD-BM-001-计费引擎.md |

### 3.2 流水号规则

1. 流水号在域内全局唯一、从 001 开始，一经分配不复用（文档作废后编号保留，不回收）；
2. 编号隐含优先级：001~099 为核心（P0）模块，100~199 为重要（P1）模块，200+ 为扩展（P2）模块；
3. 文档废弃时在文件名末尾追加 `-deprecated` 并移入所在文件夹的 `_deprecated\` 子目录，不删除。

### 3.3 关联编号

| 对象 | 编号格式 | 示例 |
| --- | --- | --- |
| 业务规则 | `R-<域码><两位流水>`，域内唯一 | R-MD01、R-TM07 |
| 验收用例 | `A<两位流水>`，文档内唯一 | A01 |
| 开放问题 | `Q<两位流水>`，文档内唯一 | Q01 |
| 非功能需求 | `N<两位流水>`，文档内唯一 | N01 |
| 原型页面 | 原型编号对齐 PRD 编号：`P<PRD流水号>-<页面流水>` | P001-03（销售订单 PRD 第 3 个页面） |

## 4. PRD 文档模板

新建 PRD 必须按以下骨架编写（章节可按模块裁剪，但顺序与编号不得改变；不适用章节保留标题并注明"不适用"）：

```markdown
# PRD-<域码>-<流水号> <文档名称>

| 文档属性 | 内容 |              ← 文档信息表：编号/名称/所属服务/模块/版本/创建日期/作者/评审人
## 版本记录                          ← 表：版本/日期/修订人/修订说明
## 1. 背景与目标                     ← 业务背景、产品目标、用户价值
## 2. 需求范围                       ← 本期范围 / 不涉及 / 依赖前置
## 3. 角色与权限                     ← 涉及角色、操作权限矩阵
## 4. 业务流程                       ← 端到端流程图 + 关键场景说明
## 5. 功能需求                       ← 按功能模块逐一展开（列表/新建/编辑/删除/导入导出/…）
## 6. 数据模型                       ← 实体、字段定义表、实体关系
## 7. 业务规则                       ← 规则表（R-xx：规则描述/触发条件/异常处理）
## 8. 状态机                         ← 单据/档案状态定义与流转（含逆向操作）
## 9. 接口需求                       ← 服务间接口与事件（编号/方向/触发/报文要点）
## 10. 非功能需求                    ← N01…（性能/安全/审计/兼容）
## 11. 验收标准                      ← A01…（可测量的预期结果）
## 12. 开放问题                      ← Q01…（问题/影响/建议）
```

## 5. 内容编写规范

### 5.1 字段定义表

功能中每个录入/显示字段必须落入字段定义表，统一列结构：

| 列 | 说明 |
| --- | --- |
| 字段名称 | 中文名，与界面一致 |
| 字段编码 | 大写下划线，如 `CUSTOMER_ID`（列表展示字段可省略） |
| 必填 | 是/否/条件（写明条件） |
| 类型与长度 | 文本(n)/数值/布尔/日期/枚举/数据字典/子表 |
| 默认值 | 无则写"—" |
| 校验与说明 | 唯一性、格式、联动、取值来源、业务含义 |

### 5.2 业务规则

1. 每条规则有唯一编号（R-域码+流水），规则表述 = 触发条件 + 处理逻辑 + 异常/提示；
2. 规则必须可测试：避免"适当""合理"等模糊词，数量、比例、状态写明确值；
3. 跨文档引用规则时写编号不复制内容（如"见 R-MD03"）。

### 5.3 状态机

1. 单据状态用表格定义：状态 / 允许操作 / 前置状态 / 后置状态 / 备注；
2. 每个正向操作必须定义对应逆向操作及其约束（如"反审核"仅"审核"状态可执行）；
3. 状态流转图使用 mermaid `stateDiagram-v2` 或 ASCII 图，二选一，同一文档内保持一致。

### 5.4 流程图

1. 端到端流程使用 mermaid `flowchart` 或 ASCII 图；
2. 图中节点使用业务单据名称+动词（如"发货订单-审核"），跨服务的节点以"〔服务码〕"前缀标注，如"〔TM〕运单-提货"。

### 5.5 验收标准

每条用例 = 前置条件 + 操作/输入 + 预期结果（含提示文案）；预期结果必须可验证。

### 5.6 语言与命名

1. 全文简体中文；标点使用中文全角（表格内代码、编码除外）；
2. 界面按钮、菜单以【】标注，如【新建】【导入】；
3. 术语使用《统一术语表》标准词（PRD-SPEC-002），文档内不再重复定义通用术语；
4. 数值精度：金额 2 位小数、数量/重量/体积 ≤3 位小数、汇率 4 位小数、比例 2 位小数且以百分数表述；
5. 日期时间格式 `YYYY-MM-DD`、`YYYY-MM-DD HH:mm`。

### 5.7 禁止事项

1. **所有文档一律不添加引用来源、参考文献、参考文件、对标产品对照等溯源信息**；
2. 不使用"参考某某系统""如某某产品"之类表述，功能描述直接以本产品口径撰写；
3. 不在 PRD 中粘贴内部文件路径、临时文件位置等技术过程信息；
4. 不出现"待开发确认"这类无归属的待办——未决事项一律进入"开放问题"并编号。

## 6. 版本与评审管理

| 状态 | 含义 | 进入条件 |
| --- | --- | --- |
| 草稿 | 撰写中 | 创建即可 |
| 评审中 | 完整成稿，发起评审 | 模板章节完整、无开放的问题项遗漏 |
| 已发布 | 评审通过，作为开发依据 | 评审人签字/确认记录 |
| 已废弃 | 被新版本或新文档取代 | 文件名追加 `-deprecated` 移入 `_deprecated\` |

1. 版本号：初稿 V1.0；评审修订 V1.1、V1.2…；结构性重写（范围/架构变化）升 V2.0；
2. 每次修改必须更新"版本记录"表；
3. 已发布文档的修改需重新评审受影响章节。

## 7. 需求—PRD—原型协作流程

```
01.需求管理（需求单/调研记录）
   → 03.PRD管理（按本规范编写 PRD，开放问题回溯需求方）
   → 02.原型管理（原型页面按 3.3 节 P 编号命名，遵循 99.原型规范）
   → 评审：PRD 与原型同审，评审通过后 PRD 状态置"已发布"
```

1. PRD 是原型的唯一依据：原型页面必须能映射到 PRD 功能点；
2. 原型评审中发现的字段/规则调整，先改 PRD 再改原型，保持一致；
3. 需求变更：需求方提出 → 评估影响面 → 更新 PRD（版本记录留痕）→ 通知原型与开发。
